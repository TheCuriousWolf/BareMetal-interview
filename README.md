# simeval: simulated evaluation of off-the-shelf robot policies

A small framework for evaluating pretrained manipulation policies (VLAs served over an API or run locally) on
household tasks in MuJoCo. The motivating evaluation is **Dream Labs Dream-1 on a bimanual YAM station, picking up a
sponge and scrubbing a stain off a counter**. Robots, grippers, tasks and model backends are each swapped by config.

```
python scripts/run_eval.py configs/evals/sponge_dream.yaml                                   # Dream-1, 5 episodes
python scripts/run_eval.py configs/evals/sponge_dream.yaml --set policy=configs/policies/hold.yaml
python scripts/run_eval.py configs/evals/sponge_dream.yaml --set level=full episodes=10 latency_mode=realtime
python scripts/run_eval.py configs/evals/sponge_dream.yaml --set robot=configs/robots/yam_single.yaml
python scripts/run_eval.py configs/evals/pick_place_dream.yaml --set task.scene_overrides.object.start_xy.nominal=[-0.1,0.0]
```

Outputs land in `runs/<name>/`: `config.json` (everything that defined the run), one `episode_XXX.json` (metrics,
stage times, sampled scene parameters, seed) and `episode_XXX.mp4` (all cameras, as the policy saw them) per episode,
and `summary.json` (aggregates with confidence intervals).

## Setup

```
conda activate agent            # Python 3.10; any env with the packages below works
pip install mujoco==3.3.7 dreamlabs-client==1.1.7 numpy pillow pyyaml imageio imageio-ffmpeg pytest
cp .env.example .env            # put DREAM_API_KEY=... in .env (git-ignored)
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest      # 9 checks, ~7 s, no API calls
```
Rendering is headless (`MUJOCO_GL=egl`, set by the script).

## Layout

```
robot_models/                 everything robot-specific
  yam/                        urdf/yam.urdf, meshes/, calibration/, robot.yaml
  grippers/yam_linear/        stock YAM parallel gripper (gripper.xml generated by build_gripper.py)
  grippers/parallel_jaw/      generic two-finger gripper for robots without their own
scenes/                       one environment file per task: fixtures, objects, start/target params, scoring thresholds
configs/
  robots/                     robot model + gripper + mounts (+ station cameras)
  tasks/                      task class + scene file + instruction + time limit + scene overrides
  policies/                   model backend, checkpoint, observation/action mapping
  evals/                      robot + task + policy + episodes + seed + randomization level + latency mode
simeval/
  sim/                        shared simulation tools: robot spawning, scene composition, cameras, contacts,
                              randomization, SimEnv (20 Hz control over 500 Hz physics)
  tasks/                      Task base class, sponge_scrub, pick_place
  policies/                   Policy / ApiPolicy / LocalPolicy, Dream Labs adapter, baselines
  eval/                       episode runner, metrics aggregation
  registry.py                 names -> classes; any "module:Class" also works
scripts/run_eval.py           CLI
tests/                        scoring and swap checks
```

## Design decisions

### Simulator: MuJoCo + MjSpec
* Contact-rich manipulation at good fidelity, fast on CPU, headless rendering, cloth/flex for the towel task later.
* The Dream Labs YAM example is MuJoCo with cameras calibrated on the real station; reusing that calibration is the
  largest lever on the visual sim2real gap for a pretrained VLA.
* `MjSpec` composes scenes programmatically: the robot description is loaded once per mount and attached at a frame
  with a name prefix. No XML string templating; the scene is rebuilt per episode so physical parameters can vary.
* Isaac Lab was ruled out for setup cost and an 8 GB laptop GPU; PyBullet for contact quality and rendering; robosuite
  and ManiSkill because their own robot/task abstractions would have to be bent around a bimanual YAM.
* Everything simulator-specific sits in `simeval/sim/`. Tasks use the MjSpec API to add bodies; policies never see it.

### Robots: data, not code
* `robot_models/<name>/robot.yaml` names the URDF (or MJCF), base and flange links, joint list, home pose, actuator
  gains, gripper mount frame and robot-mounted cameras. The loader adds position actuators, attaches the gripper at the
  flange, adds wrist cameras, and drops URDF geometry whose meshes were never shipped.
* `configs/robots/*.yaml` choose the robot model, the gripper and the **mounts**: `{left: pose, right: pose}` for a
  bimanual station or `{right: pose}` for a single arm. The mount name prefixes everything (`left_joint1`,
  `right_tcp`, camera role `right_wrist`), so tasks and policies address arms by mount name only.
* Grippers are separate folders with a common contract: fingers along −z of the root body, a `tcp` site, finger
  bodies for grasp detection, and an opening in **[0, 1]** regardless of stroke. Policies and tasks never see
  gripper-specific units. The YAM uses its stock linear gripper because Dream-1 was trained on images of it;
  `gripper: parallel_jaw` swaps in the generic one (tested).
* New robot = drop URDF + meshes in `robot_models/<name>/`, write `robot.yaml`, point a robot config at it.

### Tasks: scene file + scorer
* A scene file (`scenes/*.yaml`) holds all geometry and start/target parameters. Every value is either fixed or a
  `{nominal, range | jitter | choices, group}` record. Task configs can override any of them (`scene_overrides`, or
  `--set task.scene_overrides...` on the command line).
* A `Task` subclass builds the scene and scores it **from ground-truth simulator state only** — never from anything
  the policy reports.
* Scoring is **staged**: each stage records the first sim time it was reached. Zero-shot policies mostly fail
  long-horizon tasks; a binary success rate alone would rank them all at 0 and hide real differences.
* New task = scene file + Task subclass (`build`, `sample_task`, `step`, `success`) + a line in the registry.
  `pick_place` is the second example: object start pose and target region are scene parameters.

### The sponge task and its scoring
* Counter, sponge (9 × 6 × 3.5 cm, 15–50 g) and a stain made of ~80–100 thin visual cells inside an irregular blob.
* A cell loses dirt in proportion to how far the sponge's contact face **slides over it** while the sponge presses
  the counter with **≥ 0.5 N** and is **held by the gripper** (configurable). Placing a sponge on the stain, or pushing
  a loose one around, does not count. These properties are unit-tested.
* Cleaned cells fade on camera, so a closed-loop policy can see its own progress.
* Stages: `reached` (TCP within 6 cm) → `grasped` (both fingers in contact) → `lifted` (+2 cm while held) →
  `stain_contact` → `half_clean` → `clean` (≥ 80 % of cells, = success).
* Also recorded: cleaned fraction and dirt removed (continuous), peak sponge pressure, peak robot–counter force,
  arm–arm contact steps, sponge dropped (ends the episode), grasped steps, query latency (mean, p95), joint-limit
  clipping rate and worst overshoot, action jerk.

### Models: one interface, two plumbing bases
* `Policy`: `reset(instruction)`, `observe(obs)` at the policy's frame rate, `act(obs) -> ActionChunk`, `close()`.
  The policy declares its observation period, warm-up time (frame history) and how many chunk rows to execute
  before re-querying.
* `ApiPolicy` adds endpoint, `checkpoint`, API key from an environment variable named in config, retries and latency
  timing. `LocalPolicy` adds `checkpoint`, `device`, `load()`.
* Observation is robot-neutral (camera role → image, mount → joints + gripper). Each adapter maps roles and mounts
  to its provider's keys through `camera_map` / `arm_map` in config.
* The Dream adapter reproduces the observation contract of Dream's own YAM sim: 9 frames per camera 0.2 s apart,
  320 × 176 JPEG q85, station keys for `dream-1-beta`, absolute joint chunks back. `checkpoint` selects any Dream
  model, including fine-tunes.
* New provider = subclass `ApiPolicy` or `LocalPolicy`, implement `act` (and `observe` if it keeps history), add a
  config. Reference it by registry name or `module:Class`.

### Rigor and sim2real
* **Paired, seeded episodes.** Episode *i* uses `seed + i`; the same seed and level produce the same scene for every
  policy (tested), so policies are compared on identical episodes.
* **Randomization levels.** `none` (one canonical scene), `pose` (sponge pose and stain location/shape), `full`
  (+ sponge size/mass/friction, counter friction and colour, lighting, ±1 cm / ±1° top-camera extrinsics, stain
  colour). Reporting per level separates task difficulty from robustness. Every sampled value is saved per episode.
* **Statistics.** Success rate with a 95 % Wilson interval (sane at 0/n), mean and std of continuous metrics, per-stage
  reach rates and times. Baselines (`hold`, `random`) bound the metrics from below.
* **Latency.** `hold` pauses physics during inference (policy quality in isolation, like Dream's own sim);
  `realtime` holds the last target for the measured round trip in sim time, as a synchronous controller on the real
  station would.
* **Matched to the real station:** calibrated camera intrinsics and extrinsics, 640 × 480 sensor cropped to 640 × 360
  as in station recordings, the model's own image size and compression, 20 Hz control, position servos with force
  limits, gravity-compensated arm, gripper force limit 22 N.
* **Known gaps:** the sponge is a rigid body with compliant contact, not deformable foam; the stain is an abstract
  dirt map (no liquid, no visual smearing); arm collisions use convex hulls of the URDF link meshes (the gripper uses
  a proper convex decomposition); friction and gains are sim tuning, not hardware identification; the scene is not
  photorealistic.
